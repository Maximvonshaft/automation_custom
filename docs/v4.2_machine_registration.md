# v4.2 Machine Registration and Binding

## Purpose

Milestone 3 introduces the machine registration and machine binding boundary for the v4.2 Controlled Operator Package.

The goal is to ensure that a signed job plan can only run on the intended tenant and machine, and that HQ can disable or revoke machines before issuing new work.

## Current baseline

The existing signed job validation path already checks:

- Ed25519 signature;
- expected tenant id;
- expected machine id;
- allowed mode;
- expiry;
- forbidden actions.

This milestone formalizes how the local machine id is represented, where local registration state lives, and how revocation semantics should be interpreted.

## Local machine registration file

Default path:

```text
%USERPROFILE%\.customsops\machine_registration.json
```

Override for tests or controlled packaging:

```text
CUSTOMSOPS_MACHINE_CONFIG_ROOT=<directory>
```

Then the registration file is:

```text
<CUSTOMSOPS_MACHINE_CONFIG_ROOT>\machine_registration.json
```

## Registration contract

The registration file must contain:

```json
{
  "tenant_id": "tenant_demo",
  "machine_id": "machine_demo",
  "machine_fingerprint_sha256": "<64 hex chars>",
  "agent_version": "4.0.0",
  "operator_package_version": "0.0.0-skeleton",
  "registration_status": "active",
  "registered_at_utc": "2026-05-28T00:00:00Z",
  "public_key_id": "optional-key-id"
}
```

Supported registration statuses:

- `pending`: registration exists but is not approved for signed job execution;
- `active`: signed job execution may proceed if the signed job also validates;
- `revoked`: machine must not execute new work;
- `disabled`: machine must not execute new work.

## Machine fingerprint

The local machine fingerprint is a SHA-256 hash derived from stable local metadata:

- hostname;
- operating system;
- OS release;
- architecture;
- MAC-derived node identifier.

The fingerprint is not a credential. It is used for support, machine binding, and registration audit.

## Binding model

The signed job plan must include:

```json
{
  "tenant_id": "...",
  "machine_id": "..."
}
```

The Local Agent must verify that these values match the local expected tenant and machine. Existing `validate_signed_plan(...)` already rejects wrong tenant and wrong machine.

## Revocation semantics

Revocation is enforced primarily at the Control Plane:

1. a revoked machine must not receive newly signed job plans;
2. existing short-lived jobs expire quickly;
3. local client should fail closed if local registration status is `revoked` or `disabled`;
4. local client should fail closed if local registration status is `pending`.

This milestone defines local helpers and tests for these semantics. Future milestones should wire the helpers into the operator launcher and signed-job execution flow.

## Security boundaries

- Machine registration does not authorize finalization actions.
- Machine registration does not move country pack content to `agent/`.
- Machine registration does not allow local Excel-to-executable-plan compilation.
- Machine registration does not store production ASYCUDA credentials.
- Machine registration does not include signing private keys.

## Acceptance criteria

- Machine registration schema exists.
- Local machine registration parser exists.
- Invalid, missing, pending, revoked, and disabled registrations fail closed.
- Machine fingerprint is deterministic for the same input parts.
- Signed job wrong-machine validation remains tested.
- No Submit/Register/Payment/tax-finalizing actions are added.
- No country pack is moved into `agent/`.

## Follow-up work

A later PR should wire active registration into the operator package launcher and Control Plane registration flow. This milestone intentionally avoids full registration API implementation and external release approval.
