# v4.2 Operator Package Skeleton

## Purpose

This document defines Milestone 2 for the v4.2 Controlled Operator Package. It creates a repository-level skeleton for a future Windows operator package without approving external distribution and without changing runtime behavior.

Milestone 2 follows the Milestone 1 packaging boundary audit. The package skeleton must respect the boundary manifest and remain source-safe.

## Current status

- v4.1 is an internal Release Candidate.
- v4.2 planning documents are merged.
- Milestone 1 packaging boundary audit is merged.
- This milestone defines skeleton packaging files only.
- No external operator package is approved.

## Skeleton objectives

The skeleton defines:

1. Windows operator package directory structure.
2. A launcher entrypoint placeholder.
3. A build manifest schema.
4. A checksum generation path.
5. A support diagnostics script.
6. Tests that confirm the skeleton does not include country pack, server-only paths, source release artifacts, or finalizing actions.

## Non-goals

This milestone does not:

- produce a production installer;
- release an external package;
- add Submit/Register/Payment/tax-finalizing automation;
- move country pack content into `agent/`;
- compile executable job plans locally;
- distribute source tree to operators;
- include real customer data;
- include production credentials.

## Proposed package layout

```text
packaging/windows_operator/
  README.md
  operator_launcher.ps1
  package_skeleton.ps1
  build_manifest.schema.json
  support_diagnostics_manifest.schema.json
```

The future generated package layout is expected to be:

```text
CustomsOpsOperator/
  operator_launcher.ps1
  README.md
  BUILD_MANIFEST.json
  checksums.sha256
  diagnostics/
  evidence/
  config/
```

The generated package must not contain:

```text
control_plane/
control_plane/packs/
delivery_packs/
tests/
.git/
lab/
outputs/
*.xlsx
*.pem
*.key
*.p12

```

## Launcher contract

The launcher is a controlled entrypoint. It should eventually:

- verify it is running inside an approved package directory;
- show package version and build manifest;
- require tenant and machine binding;
- call only signed-job execution paths;
- display SafeBrake/fillOnly mode clearly;
- avoid exposing country pack or job compilation internals.

Current milestone launcher is a placeholder and must fail closed unless explicitly wired in a later implementation PR.

## Build manifest contract

Every future package must include `BUILD_MANIFEST.json` with at least:

- package_name;
- package_version;
- source_repo;
- source_commit;
- build_timestamp_utc;
- build_host;
- release_classification;
- included_files;
- excluded_patterns;
- checksum_file;
- no_finalization_actions;
- country_pack_excluded;
- local_compilation_disabled;

## Checksum contract

A future package build must generate `checksums.sha256`. The checksum file must cover all package files except the checksum file itself.

## Support diagnostics contract

Support diagnostics must collect only non-secret metadata by default:

- package manifest presence;
- OS / PowerShell / Python versions;
- directory layout;
- evidence folder file hashes;
- environment readiness summary;
- no credentials;
- no customer manifest rows;
- no raw screenshots unless separately approved.

## Acceptance criteria for Milestone 2

- Windows package skeleton directory exists.
- Launcher placeholder exists and is explicitly not production-ready.
- Build manifest schema exists.
- Package skeleton script exists but is not an external release builder.
- Support diagnostics script exists and excludes secrets by default.
- Tests assert the skeleton does not include server-only paths or forbidden actions.
- No runtime code changes are made.

## Handoff to Milestone 3

Milestone 3 should implement machine registration and binding. The skeleton created here must not be treated as externally distributable until machine binding, signed-job-only hardening, release approval, and artifact checksums are complete.
