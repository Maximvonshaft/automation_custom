# v4.2 Signed-Job-Only Operator Flow

## Purpose

Milestone 4 hardens the local operator execution entrypoint so that the operator package can only run HQ-issued signed job plans on an active registered machine.

This milestone wires the operator package launcher to a signed-job-only local Python entrypoint. It does not add Submit/Register/Payment/tax-finalizing automation, does not move country pack content into the Agent, and does not allow local Excel-to-executable-plan compilation.

## Current baseline

Previous milestones established:

- package boundary audit;
- Windows operator package skeleton;
- machine registration schema and local machine identity helpers;
- signed job validation that already checks signature, tenant, machine, mode, expiry, and forbidden actions.

## Operator flow

```text
operator_launcher.ps1
  -> requires signed job plan path
  -> requires machine registration file
  -> requires trusted public key PEM
  -> calls python -m agent.customsops_agent.operator_flow
       -> load local machine registration
       -> require registration_status == active
       -> load trusted signing public key
       -> call run_signed_job(...)
            -> validate Ed25519 signature
            -> validate tenant_id
            -> validate machine_id
            -> validate mode
            -> validate expires_at
            -> reject forbidden actions
            -> execute allowed steps
            -> produce evidence bundle
```

## Local responsibilities

The local operator flow may:

- read local machine registration state;
- load a trusted public key;
- verify signed jobs through the existing validation path;
- invoke existing Agent execution and evidence creation.

The local operator flow must not:

- parse Excel into executable steps;
- compile job plans;
- read country pack content;
- generate signatures;
- run finalization actions;
- store production ASYCUDA credentials.

## Rejection cases

The operator flow must reject:

- missing public key;
- unsigned job;
- tampered job;
- expired job;
- wrong tenant;
- wrong machine;
- unsupported mode;
- forbidden action;
- pending machine registration;
- revoked machine registration;
- disabled machine registration.

## Launcher behavior

The Windows launcher is no longer an inert placeholder. It is still not a production installer, but it is now a controlled wrapper around the signed-job-only Python module.

Required launcher inputs:

```powershell
-SignedJobPlan <path>
-MachineRegistration <path>
-PublicKeyPem <path>
-EvidenceRoot <path>
-ForegroundWindowTitle <optional>
-RealGui <optional switch>
```

## Security boundary

Signed-job-only means the local system does not decide what to execute. It verifies HQ-authorized work and executes only allowed actions already present in a signed plan.

HQ remains responsible for:

- manifest parsing;
- declaration model creation;
- country pack resolution;
- job plan compilation;
- signing;
- revocation;
- release gating.

## Acceptance criteria

- `operator_flow.py` exists.
- Launcher calls the signed-job-only module.
- Tests prove active machine registration allows the flow.
- Tests prove pending/revoked/disabled registrations fail closed.
- Tests prove missing public key fails closed.
- Tests prove wrong machine signed job fails closed.
- Tests prove forbidden action signed job fails closed.
- Existing no-finalization and no-country-pack boundaries remain unchanged.

## Non-approval statement

This milestone does not approve external operator package distribution. It only hardens the local operator execution entrypoint before later packaging and pilot release gates.
