# v4.2 Package File Classification

## Purpose

This document classifies repository paths for the future v4.2 Controlled Operator Package. The goal is to define which files may enter a local operator artifact and which files must remain server-side, test-only, or excluded.

This document does not approve an external operator package. It is a boundary audit for later packaging work.

## Current release position

- `v4.1` is an internal Release Candidate.
- `v4.2` planning documents have been merged.
- No external operator package is approved.
- The local Operator Package must not receive country pack production content, server-side compilation logic, credentials, real customer data, or executable finalization actions.

## Classification model

Every path should be classified into one of the following groups:

| Class | Meaning | Can ship to operator? |
|---|---|---|
| `operator_local_candidate` | Potentially safe local runtime files after implementation review | Candidate only |
| `server_only` | Control Plane, country pack, signing, compilation, tenant, or business-rule authority | No |
| `test_only` | CI/test fixtures and regression tests | No |
| `docs_only` | Documentation; selected runbooks may ship, internal planning docs should not | Case-by-case |
| `excluded` | Outputs, lab artifacts, downloaded bundles, real samples, secrets, archives | No |

The local operator package may eventually include a minimal subset of:

```text
agent/customsops_agent/config.py

agent/customsops_agent/action_executor.py
```

These are candidates only. They still require a later package builder that strips source where appropriate and produces a controlled artifact with checksum, version, and release evidence.

## Server-only files

The following must not ship in an external operator package:

```text
control_plane/
control_plane/app/services/job_compiler.py
control_plane/app/services/declaration_job_compiler.py
control_plane/app/services/manifest_intake.py
control_plane/app/services/declaration_model_builder.py
control_plane/packs/
control_plane/**/packs/**
delivery_packs/
```

Reason: these paths contain or may lead to server-side authority, country pack logic, manifest-to-declaration transformations, job compilation logic, release construction packages, or internal implementation strategy.

## Test-only files

The following must not ship in an external operator package:

```text
tests/
```

Reason: tests may encode internal expectations, templates, failure gates, forbidden boundaries, and sanitized but still strategically useful behavior descriptions.

## Docs handling

Documentation should be split in a later milestone:

- operator runbook: can ship after redaction review;
- support diagnostics runbook: can ship after redaction review;
- planning docs, threat models, and implementation roadmaps: internal only;
- release checklists: internal only unless converted to an operator-facing support document.

```text
.git/

__pycache__/
.pytest_cache/
.ruff_cache/
.bandit/
outputs/
lab/
*.zip
*.xlsx

```

## Security rationale

The operator package must not allow a local party to reconstruct the ASYCUDA automation system from source, country pack files, coordinates, or server-side job compilation logic. The local artifact must only execute signed jobs created by HQ-controlled systems.

## Audit result for Milestone 1

Milestone 1 creates the first formal package boundary manifest and tests. It does not produce an operator package. It is a prerequisite for Milestone 2, where a package skeleton can be created safely.

## Required follow-up

Before any actual package builder exists, the following must be implemented in later PRs:

1. package builder uses the manifest as allowlist/exclusion source;
2. package output is scanned for server-only paths;
3. artifact checksum and build manifest are generated;
4. local package cannot compile signed plans;
5. external release requires separate approval.
